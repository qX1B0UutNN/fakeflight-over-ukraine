# FakeFlight Ukraine Dataset: Implementation Plan

## 1. Goal

Generate synthetic camera frames along manually drawn flight trajectories. A
rendering run samples one trajectory, renders it from one georeferenced
orthophoto, and stores everything required to reproduce the run in `meta.json`.

Version 1 uses a flat ground plane and fixed flight altitude. It does not use a
DEM, terrain correction, lens distortion, or dynamic altitude.

## 2. Dataset Layout

```text
dataset/
|-- location/
|   |-- boryspil-airport/
|   |   |-- geoms/
|   |   |   |-- bounds.geojson
|   |   |   `-- traj.geojson
|   |   |-- ortho/
|   |   |   `-- <provider>_<zoom>.tif
|   |   |-- cam-configs/
|   |   |   `-- <camera>.yaml
|   |   `-- motion-configs/
|   |       `-- <motion>.yaml
|   `-- <another-location>/
`-- renders/
    |-- renders.csv
    `-- <location>-<trajectory-id>-<ortho-source>-<coolname>/
        |-- meta.json
        `-- frames/
            `-- frame-000000.png
```

Rules:

- Location folders contain inputs only. Generated output always goes under
  `dataset/renders`.
- Trajectories are read from `geoms/traj.geojson` and must use the same CRS as
  the selected ortho.
- `trajectory_id` is the zero-based GeoJSON feature index. One rendering run
  samples and renders exactly one feature.
- A default run name ends with a random word generated by `coolname`.
- `render_name` overrides the complete generated name.
- Run names must be unique in both the filesystem and `renders.csv`.
- Existing output is never overwritten.

## 3. Rendering CLI

`scripts/render.py` is the single pipeline entry point. It intentionally keeps
only the milestone stages; sampling and rendering implementations live under
`src/sampling` and `src/rendering`.

Example:

```bash
python scripts/render.py \
  --camera_config=dataset/location/boryspil-airport/cam-configs/high-altitude-360m.yaml \
  --motion_config=dataset/location/boryspil-airport/motion-configs/default.yaml \
  --trajectory_file=dataset/location/boryspil-airport/geoms/traj.geojson \
  --trajectory_id=1 \
  --source_ortho=dataset/location/boryspil-airport/ortho/yandex_19.tif
```

Optional arguments:

- `render_name`: complete run-name override.
- `renders_dir`: output root, defaulting to `dataset/renders`.
- `max_frames`: positive frame limit for test renders.

The stages are:

1. Resolve and reserve a unique run name.
2. Load camera, motion, trajectory, and ortho inputs.
3. Sample only the selected trajectory.
4. Render its frames.
5. Write an atomic, self-contained `meta.json`.
6. Append the completed run to `renders.csv`.

There is no intermediate `trajectory-samples.json`.

## 4. Camera Configuration

Camera configurations are human-authored YAML files:

```yaml
version: 1

image:
  width_px: 1920
  height_px: 1080

sensor:
  width_mm: 13.2
  height_mm: 7.425

lens:
  focal_length_x_mm: 8.8
  focal_length_y_mm: 8.8
  skew_px: 0.0
  principal_point_x_px: null
  principal_point_y_px: null
```

When a principal point is `null`, the image center is used. The intrinsic
matrix is calculated as:

```text
fx_px = focal_length_x_mm * width_px / sensor_width_mm
fy_px = focal_length_y_mm * height_px / sensor_height_mm

K = [[fx_px, skew_px, cx_px],
     [0,     fy_px,   cy_px],
     [0,     0,       1]]
```

## 5. Motion Configuration

Motion configurations replace the former movement configurations:

```yaml
version: 1

speed_mps: 20.0
camera_fps: 5.0
altitude_m: 120.0

orientation_deg:
  yaw: 0.0
  pitch: 0.0
  roll: 0.0

orientation_oscillation: null
position_oscillation: null
random_seed: 42
```

Optional orientation and position oscillations are sinusoids. Their initial
phases come from `random_seed`, so runs with identical inputs are deterministic.

## 6. Coordinates and Camera Pose

World coordinates follow the projected ortho CRS: X is easting, Y is northing,
and Z is meters above the flat ground plane. Camera coordinates use the OpenCV
convention: X points right, Y down, and Z forward.

The base camera is nadir-looking. Zero orientation points image-up along the
trajectory. Orientation offsets are applied in base heading, yaw, pitch, and
roll order. Metadata stores a 4-by-4 world-to-camera matrix:

```text
p_camera = T_world_to_camera @ p_world
```

## 7. Trajectory Sampling

The sampler accepts `LineString` and single-part `MultiLineString` features.
For the selected feature it:

1. Samples the first position at distance zero.
2. Uses `distance_step_m = speed_mps / camera_fps`.
3. Uses `timestamp_sec = frame_index / camera_fps`.
4. Interpolates positions by cumulative metric distance.
5. Calculates heading from the local path tangent.
6. Applies configured position and orientation oscillations.
7. Builds the final camera pose and extrinsic matrix.

The endpoint is not appended when it is less than a full sample step after the
last frame.

## 8. Frame Rendering

For every sampled camera pose, the renderer casts rays through the output-image
corners, intersects them with the ground plane, maps the footprint into source
raster pixels, reads the required raster window, and applies a perspective
warp. A run fails when the camera does not see the ground or the footprint lies
outside the orthophoto.

## 9. Run Metadata

Every run has one `meta.json` with schema version 2. It includes:

- Run name, UTC rendering timestamp, and location.
- Ortho name, path, and CRS.
- Camera config name, path, and the complete YAML values.
- Motion config name, path, and the complete YAML values.
- Derived camera intrinsic matrix and image dimensions.
- Trajectory ID and source path.
- Every sampled frame pose, extrinsic matrix, and relative image path.

Config contents are copied into metadata so a run remains reproducible if its
original YAML files are changed or lost.

## 10. Render Registry

`dataset/renders/renders.csv` records completed runs with these columns:

```text
run_name,rendered_at,location,trajectory_id,source_ortho,camera_config,motion_config,frame_count
```

The renderer checks both the registry and output directories for duplicates.
The registry is updated only after all frames and `meta.json` have been written.
